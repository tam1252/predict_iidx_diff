# textage.cc 譜面データ解読記録

beatmania IIDXの譜面サイト [textage.cc](https://textage.cc) から、HTMLに埋め込まれた譜面データをPythonでJSONに変換するまでの試行錯誤の記録。

---

## 出発点

textage.ccの各譜面ページはHTML + JavaScriptで構成されており、譜面データは`<script>`タグ内のJavaScript変数として埋め込まれている。描画エンジン本体は外部ファイル`bms2jsh.js`で、これをブラウザが読み込んで実行することで譜面が描画される。

```html
<script type="text/javascript" src="../bms2jsh.js"></script>
<script type="text/javascript">
    title = "Verflucht";
    bpm = "157";
    measure = 84;
    sp = [,,"x010cb@02...", "#R1R3XEV...", ...];
    c1[21] = [[7, 64, 62]];
    tc[5] = ["1570"];
</script>
```

やりたいことはシンプルで、この`sp[]`、`c1[]`、`tc[]`をPythonで解読して、各ノーツを`{measure, pos, key, type}`のリストとして出力すること。

参考にしたのは [lmtak氏のブログ](https://lmtak.hateblo.jp/entry/2022/04/30/180000) による先行解析。ただしブログの情報だけでは詳細が足りない部分が多く、後から`bms2jsh.js`の実ファイルを直接入手したことで一気に解読が進んだ。

---

## ステップ1: 全体構造の把握とブログ解析

まずlmtak氏のブログ2本を読み込んだ。

- sp配列の各エントリが1小節分のノーツデータであること
- `#`始まりと`x`（hex）始まりの2種類のエンコードがあること
- c1/c2 がチャージノーツの定義であること

これをもとに最初のデコーダーを書いたが、Verflucht SP-Lのノーツ数（正解2401）に対して大幅にずれた値しか出なかった。

---

## ステップ2: bms2jsh.jsの入手

ブログの推測情報だけでは詰まったので、textage.ccのページソースから`bms2jsh.js`の実ファイルを直接取得した。これが解読の転換点だった。

実ファイルを見ると、`#`形式のswitch文が全コマンド分定義されており、各コマンドの`v2p`（ステップ間隔）、`v2s`（開始オフセット）、`v2t`（処理タイプ）が正確に把握できた。

**ブログの記述と実際の乖離（主要なもの）：**

| コマンド | ブログの v2p | 実際の v2p |
|---------|------------|-----------|
| `R` | 48 | 96 |
| `P` | 64 | 48 |
| `X` | 直接指定と誤解 | v2p=24 の v2t=1 コマンド |

---

## ステップ3: `#`形式の解読

### 処理タイプの定義

bms2jsh.jsのswitch文から3種類の`v2t`を確認。

- **v2t=0**: コマンド文字の直後1文字がレーン番号、`v2p`間隔で`v2s`から繰り返し配置
- **v2t=1**: コマンド直後の複数文字（`v2b`文字分）をBASE64 → 8進数2桁に展開し、各桁がレーン番号
- **v2t=2**: コマンド直後1文字がレーン番号 + BASE64 2文字が絶対位置（`pos = v2h * ln_n / 4096`）

### v2t=1 の ob2 展開がハマりポイントだった

当初「B64値をビット展開してレーン番号」と誤解していたが、実際は**8進数2桁**への変換だった。

JSソース:
```javascript
v2x = b64[v2o.charAt(v2k)] * 8 + 3;
ob2 = b64.charAt(v2x >> 3) + "";   // 上位3ビット → 8進上位桁
ob2 += b64.charAt(v2x & 7);        // 下位3ビット → 8進下位桁
```

つまり1文字のBASE64値から**2つのレーン番号**が得られる。各桁が 0 なら TT（スクラッチ）、1〜7 なら鍵盤。

### `_`コマンド（TT付加）

`_`は終端コマンドで、後ろにBASE64 2文字が続く場合は`pos=0, lane=0`（スクラッチ）のノーツを付加する。

```javascript
case "_":
    v2o = sdd.substring(sft+1, sft+3);  // "AA" なら pos=0, lane=0
```

### `-`コマンド（v2cリセットバグ）

**最初の重大バグ。** `-`コマンドは`v2c=1`フラグを立てる（v2t=1 の v2v 計算を変える）。
当初ループ末尾で`v2c = 0`にリセットしていたが、bms2jsh.jsを見ると**`-`以降ずっと`v2c=1`が維持される**設計だった。

```python
# ❌ バグあり
for char in sdd:
    if char == '-':
        v2c = 1
    ...
    v2c = 0  # ← ここが間違い

# ✅ 正しい
for char in sdd:
    if char == '-':
        v2c = 1
    ...
    # v2c は維持したまま
```

このバグでノーツが大量に消えていた。修正後、`#`形式の合計が大幅に改善。

## ステップ4: `x`（hex）形式の解読

`x`プレフィックスで始まる文字列は16進数形式。最初の3文字が`sft_len`（全体分割数）、その後2文字ずつが1エントリ。

```
x030 83 10 20 84 08 40 84 ...  @0b ...
^^^  ^^ ^^ ^^ ^^              ^^^
長さ  ノーツエントリ（2文字ずつ）    オフセットジャンプ
```

JSの実装:
```javascript
if (sdd.charAt(0) == "x") {
    len = parseInt(sdd.substring(1, 4), 16);  // sft_len
    sft = 4;
} else {
    len = sdd.length;
}
for (; sft < sdd.length; sft += 2, div += 2) {
    while (sdd.charAt(sft) == "@") {
        div += parseInt(sdd.substring(sft+1, sft+3), 16) * 2;
        sft += 3;
    }
    pos = Math.floor(nbar * div * 3 / len);
    // 各バイトのビットをレーン番号に変換
}
```

当初1文字ずつ処理していたが、**2文字（1バイト）単位**でレーン情報を読む必要があった。各バイトのビット 0〜7 がレーン 0〜7 に対応し、複数ビットが立っていれば同位置に複数ノーツ（同時押し）。

`@XX`が来たら`div += int(XX, 16) * 2`で空白区間をスキップ。ノーツが存在しない区間を省略する圧縮形式。

```javascript
sp[58] = sp[41];
sp[59] = sp[42];
sp[60] = sp[43];
```

参照解決を追加して2401/2401完全一致を達成。

## ステップ6: 惑星鉄道で 1633 → 406 の衝撃

Verfluchtが完璧に動いたので別の曲（惑星鉄道 SPA、正解1633ノーツ）で検証したところ**406ノーツ**という全く違う値が出た。

HTMLを見ると複数難易度のデータが`if`ブロックで共存していた。

```javascript
if (g) {
    // BEGINNER
    sp = [...];
} else if (k) {
    // HYPERベース
    sp = [...];     // ← 先に読まれる

    if (a) {
        // ANOTHER（こちらが正解）
        sp = [...];
    }
    if (l) {
        // LEGGENDARIA変種（最後に書かれているので上書きされていた）
        sp = [...];
    }
}
```

`re.finditer`で全`sp[n]=`を無条件に取得していたため、最後に書かれた`if(l)`ブロックの内容でANOTHERのデータが上書きされていた。

### 解決：深さカウントによるブロック抽出

URLのクエリパラメータ（char2）から対象難易度の変数（`a`, `k`, `h`等）を特定し、対応する`if(VAR){...}`ブロックを深さカウントで正確に抽出する`_extract_difficulty_block()`を実装した。

```python
def _extract_difficulty_block(html_text, var):
    depth = 0
    for i, ch in enumerate(region):
        if ch == '{': depth += 1
        if ch == '}':
            depth -= 1
            if depth == 0:
                return region[:i+1]
```

### char2マッピングの誤りも同時に発覚

LEGGENDARIA（URLの`X`）を`if(l)`ブロックに対応させていたが、bms2jsh.jsを確認すると：

```javascript
// char2='X' → a=1, kuro=1  （LEGGENDARIA は ANOTHER の一種）
// char2='A' → a=1
// char2='L' → l=1           （レアな LEGGENDARIA 変種）
```

`X`は`if(a)`ブロックに入る必要があった。修正後、Verflucht SP-Lも惑星鉄道 SP-Aも正しい値に。

## ステップ7: 叙情で 836 → 410 の問題

次の検証曲としてop.31 叙情（SP ANOTHER、正解836）を試すと**410ノーツ**。

まず`sp=\[`がスペースなしのケースしかマッチしない正規表現バグがあり、`sp\s*=\s*\[`に修正。それでも0ノーツ。

HTMLを詳しく見ると、叙情の`if(a)`ブロックは親ブロックのspを参照する形式だった：

```javascript
} else if (k) {
    sp = [,,"#OKcu","#XIQYguA","80", ...];   // 親ブロックの sp

    if (a) {
        // sp[5], sp[6] は親の sp を参照している
        sp = [,,"10",, sp[5], sp[6], "80", "#QGo", ...];
    }
}
```

`if(a)`ブロックだけを切り出して処理すると`sp[5]`, `sp[6]`の参照先が存在しない。

**解決策**: `if(a)`ブロックの直前にある最後の`sp=`を「親SP」としてパースし、子ブロック内の`sp[n]`参照を親の内容で解決する`parent_sp`機構を実装。

```python
def _parse_sp_block(block, parent_sp=None):
    for ref_match in re.finditer(r'sp\[(\d+)\]\s*=\s*sp\[(\d+)\]', block):
        dest, src = int(ref_match.group(1)), int(ref_match.group(2))
        sp_raw[dest] = parent_sp.get(src, '') if parent_sp else ''
```

この修正で叙情836ノーツ完全一致。

## ステップ8: チャージノーツ（CN）の処理

### c1/c2 配列の構造

```javascript
c1[measure] = [[lane, start_pos, length, flag], ...]
```

| フィールド | 意味 |
|-----------|------|
| `lane` | 0=スクラッチ、1〜7=鍵盤 |
| `start_pos` | 小節内の開始位置 |
| `length` | CNの長さ |
| `flag` | ビットフラグ（bit0=始端あり、bit1=終端あり、bit2=MSS） |

flagのデフォルトは3（始端・終端両方あり）で、始端と終端がそれぞれ1ノーツとしてカウントされる。

### c1[n]=c1[m] 参照コピー問題

惑星鉄道のc1にこのような参照があった：

```javascript
c1[21] = [[0, 64, 32]];
c1[29] = c1[21];  // 21小節と同じパターン
```

Pass 1（リテラル配列をパース）→ Pass 2（参照形式を解決）の2段階処理で対応。

### MSS（マルチスピンスクラッチ）

`flag & 4`が立っているCNがMSS。見た目は通常CNと異なるが、ノーツカウントのロジックは同じ。

## ステップ9: LNDEF と BPM変化（ソフラン対応）

### LNDEFの問題

デフォルト小節長`LNDEF=384`を固定値で使っていたが、叙情は：

```javascript
LNDEF = 288;
```

と上書きされており、曲長の計算が343秒（実際は約148秒）という大幅なずれが生じた。HTMLから`LNDEF`を動的に読み取って全計算に使う実装に変更。

### tc配列（BPM変化）

```javascript
tc[measure] = ["BBBPP", ...]
// BBB: BPM（3桁、スペースパディングあり）
// PP:  小節内位置（16進数2桁）
```

正規表現が`tc\[(\d+)\]=\[`でスペースなしのみマッチしていたバグ（`\s*=\s*`に修正）と、初期BPMの設定ミス（`tc[1]`が`pos=0`の場合はそれを初期BPMとして採用）を修正。
